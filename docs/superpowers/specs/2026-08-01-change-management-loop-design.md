# Tricoder CLI 变更管理闭环设计

## 背景与目标

TriCoder 已具备 `edit_file`、`create_file`、人工审批、安全目录绑定、Session 独立上下文和结构化审计，但用户还不能按任务查看 Agent 的净修改，也不能安全撤销最近一条任务。模型进行多处精确修改时，只能连续调用单文件工具，缺少统一补丁入口。

本轮实现三个相互配合的能力：

- Provider 可调用的 `apply_patch`，一次处理多个文件的受限 unified diff。
- 本地 `/diff`，显示当前 Session 最近一条非空任务的净文件变化。
- 本地 `/undo`，在没有外部冲突时撤销该任务的全部文件变化。

目标是形成“修改—检查—撤销”的最小闭环，同时保持现有审批、工作区、隐私和审计边界。不依赖 Git，不持久化源码快照。

## 已确认的产品语义

- `/undo` 按用户任务撤销，而不是只撤销最后一次工具调用。
- `/diff` 与 `/undo` 都指向当前 Session 最近一条非空任务变更集。
- 文件在任务完成后被用户或其他程序改变时，整次 `/undo` 拒绝执行，不覆盖外部修改。
- `apply_patch` 支持修改已有文本文件和创建新文本文件，不支持删除或重命名。
- `/undo` 可以删除上一条任务创建的新文件，但必须展示反向 diff 并再次审批。
- 变更账本仅在当前进程内存在；重启后不恢复，不把源码快照写入 SQLite 或磁盘。
- 单个任务的前后快照总量最多为 2,000,000 个字符。

## 方案比较与选择

### 方案一：Session 内存变更账本（采用）

每条普通用户任务建立一个变更事务，记录成功写入文件的前后快照。`/diff` 从快照生成正向差异，`/undo` 在验证后执行反向恢复。

该方案不依赖 Git，支持非 Git 工作区和新建文件，能区分 Agent 修改与用户已有修改，也不需要把源码复制到持久化存储。代价是退出进程后撤销能力消失，符合本轮明确的隐私边界。

### 方案二：Git 状态驱动

使用 `git diff` 展示变化并用 Git 恢复文件。实现较少，但无法可靠区分用户修改与 Agent 修改，不能覆盖非 Git 目录，也可能影响用户暂存区，因此不采用。

### 方案三：磁盘备份驱动

把任务前文件复制到本地备份目录。它可以跨重启撤销，但会额外持久化源码，需要加密、容量限制、权限和清理策略，与当前安全记忆边界不一致，因此不采用。

## 核心数据模型

新增 `src/tricoder/changes.py`，只管理内存状态，不直接解析 Provider 补丁。

### `FileSnapshot`

表示一个明确时点的文件状态：

- 规范化工作区相对路径。
- UTF-8 文本内容。
- 文件权限 mode。
- 跨平台文件身份的 `device`/`inode` 稳定值；不存在的文件用 `None` 表示。该值由文件安全层提供，`changes.py` 不依赖 `tools.py` 的私有类型。

身份与内容同时用于冲突检测：身份相同但内容改变，或内容相同但对象被替换，都视为外部变化。

### `FileChange`

包含同一路径的 `before` 与 `after`：

- 修改已有文件：二者都存在。
- 创建新文件：`before=None`、`after` 存在。
- 如果同一任务多次修改同一文件，保留第一次写入前的 `before` 和最后一次写入后的 `after`。
- 如果最终内容与任务开始前完全一致，则该路径从净变更集中移除。

### `TaskChangeSet`

表示一条普通用户任务的净变化：

- 有序 `FileChange` 集合。
- 任务开始前的 `SessionContext.modified_files` 与 `verification`。
- 任务完成后的对应结构化状态。
- 不保存任务文本、模型总结、工具输出、diff 或认证信息。

### `ChangeJournal`

每个已打开 Session 拥有独立实例：

- `begin_task(...)` 开启任务事务。
- `reserve(...)` 在审批和写入前检查快照预算。
- `record_committed(...)` 只记录已经成功落盘的真实变化。
- `seal_task(...)` 聚合净变化；空任务不覆盖上一条非空变更集。
- `latest()` 返回最近一条非空变更集。
- `clear_latest()` 仅在撤销完整成功后清除。

账本最多保留每个 Session 最近一条非空变更集。Session 切换时实例随 `ActiveSession` 一同进入内存缓存；`/clear` 和模型切换保留账本；进程退出后账本自然销毁。

## `apply_patch` 设计

新增 `src/tricoder/patches.py`，负责受限 unified diff 的纯解析和内存应用，不访问磁盘。

### 工具协议

`ToolRegistry` 注册：

```text
apply_patch({"patch": "<unified diff>"})
```

工具定义继续通过现有 Provider-native structured tool calling 发送。`patch` 必须是非空字符串。

支持：

- 一个补丁中包含多个文件。
- 一个文件包含多个 hunk。
- 修改已有 UTF-8 文本文件。
- 从 `/dev/null` 创建新的 UTF-8 文本文件。

拒绝：

- 删除、重命名、复制和二进制补丁。
- 绝对路径、`..`、敏感路径、重复目标路径和越界路径。
- 缺失 hunk 头、重叠 hunk、行号不一致、上下文不精确或尾部未消费的畸形输入。
- 新建目标已经存在，或修改目标不是普通文件。

### 三阶段执行

1. **解析与预检**：解析全部文件和 hunk；通过 `WorkspacePolicy` 解析规范路径；读取当前内容、mode 和身份；在内存应用补丁；检查整个变更集的 2,000,000 字符预算。任何错误都在审批和写入前拒绝整批补丁。
2. **审批前复核**：生成完整组合 diff 交给现有 Approver。审批后重新绑定父目录并验证所有文件身份与内容仍等于预检快照；任何目标变化都拒绝整批写入。
3. **提交**：复用安全目录绑定和单文件原子发布原语逐个提交。每次真实提交后立即记录账本。

多文件系统没有通用的整体原子替换。若第 N 个文件提交失败，工具立即用预检快照补偿已经提交的文件。补偿全部成功时返回整批失败且不留下净变化；补偿失败时返回“部分提交”，列出规范相对路径并保留账本中的实际状态，绝不把部分成功伪装成全成功或全失败。

`edit_file` 和 `create_file` 保持兼容并接入同一账本。为让 Agent 正确处理多文件修改，`ToolResult` 增加向后兼容的 `modified_paths: tuple[str, ...]`；旧工具可继续使用单数 `relative_path`，Agent 合并两者并去重。

## `/diff` 设计

`commands.py` 把 `diff` 加入无参数本地命令。它只由 Shell 调用 `SessionRuntime.diff_latest()`，不会进入 Agent 或 Provider。

- 有最近变更集时，按规范相对路径排序生成组合 unified diff。
- 修改文件显示任务前后内容；新建文件以 `/dev/null` 为旧文件。
- 展示的是账本快照，不重新解释 Git 状态，也不把当前外部修改混入结果。
- 没有可用变更集时显示“当前 Session 没有可查看的任务变更”。
- `/diff` 是只读操作，在 `--read-only` 模式仍可使用。
- diff 只发送到终端 UI，不写入审计、SQLite 或 Session 摘要。

## `/undo` 设计

`commands.py` 把 `undo` 加入无参数本地命令。它只能由 Shell 触发，Provider 工具注册表不暴露撤销能力。

### 冲突检测

`SessionRuntime.prepare_undo()` 在显示审批前完成整批复核：

- 修改文件必须仍存在，身份、内容和 mode 必须等于 `after` 快照。
- 任务新建文件必须仍存在并等于 `after` 快照。
- 任一路径不一致，整次撤销拒绝，不改变任何文件，并列出全部冲突路径。

### 审批与执行

- 验证通过后生成完整反向 unified diff。
- Shell 使用现有 `confirm()`，只有输入 `y` 或 `yes` 才继续。
- 用户确认后，`SessionRuntime.undo_latest()` 在第一次写入前重新绑定目录并再次验证全部 after 快照，关闭审批等待期间的 TOCTOU 窗口；任一变化仍然整批拒绝。
- 已有文件通过安全目录绑定和原子替换恢复 `before` 内容与 mode。
- 任务新建文件通过绑定后的身份复核安全删除。
- 用户拒绝时不改变文件，也不清空变更集。

撤销过程中若后续文件失败，运行时尝试把已撤销文件恢复到各自 `after` 快照。补偿失败时报告实际部分状态和涉及路径，保留可审计的失败结果，不声称撤销完成。

仅在所有文件恢复成功后：

- 清空最近变更集，连续再次 `/undo` 显示无可撤销变化。
- 把当前 Session 的 `modified_files` 与 `verification` 恢复为任务开始前的结构化状态。
- 更新安全 `SessionMemory` 并尝试持久化；若 SQLite 保存失败，工作区撤销仍视为已经完成，但沿用现有“记忆未持久化”警告和退出重试机制。

## Runtime 与 Session 集成

`ActiveSession` 增加可变但不持久化的 `ChangeJournal` 引用，并保留构建 Agent 时使用的同一个 `AuditLogger`，供 `/undo` 写入本地结构化事件。`SessionRuntime.run_task()` 的边界调整为：

1. 使用当前结构化上下文调用 `journal.begin_task()`。
2. 运行 `agent.run_with_context()`；工具在提交后记录变化。
3. 无论 Agent 返回成功、未完成或抛出已处理异常，都按实际落盘变化封存事务。
4. 用现有逻辑更新安全 Session memory。

任务最终失败不会丢弃已落盘变更；这些变化仍能被 `/diff` 查看和 `/undo` 撤销。普通文本任务没有写入时，不覆盖当前 Session 上一条非空变更集。

Session 创建时得到空账本；同进程内切换回旧 Session 时恢复该 Session 的账本。重启后只恢复现有安全摘要和结构化元数据，`/diff` 与 `/undo` 历史为空。

## 审计与隐私

新增结构化事件但不保存源码或补丁：

- `apply_patch`：状态、规范相对路径列表、文件数、输入字符数和总变更字符数。
- `/undo`：状态、规范相对路径列表、文件数、冲突数、补偿状态。

所有路径经过 `WorkspacePolicy` 规范化。审计不记录 `patch`、before/after 内容、diff、任务原文、Provider 原始响应或认证信息。内存账本不进入 `SessionMemory`、SQLite 或 JSONL。

## 只读、容量与失败边界

- `--read-only` 禁止 `apply_patch`、`edit_file`、`create_file` 和 `/undo`；允许 `/diff`。
- 2,000,000 字符预算按当前任务所有净变化的 before 与 after 文本字符数之和计算。
- 单文件旧工具在写入前向账本预留预算；超过预算则在审批前拒绝该次写入。先前已记录且在预算内的任务变化仍然可撤销。
- `apply_patch` 在任何审批或写入前一次性验证整批预算。
- 未知编码、二进制内容、无法读取 mode、目录身份变化和符号链接逃逸继续按现有策略拒绝。
- 所有面向终端的异常使用稳定中文消息；底层路径、临时文件名和异常自由文本不进入公共输出。

## 测试设计

### 纯模型与解析

- `FileChange` 聚合同一路径多次写入并删除净零变化。
- 快照预算的边界值、同文件更新后的重新计数和超限拒绝。
- unified diff 的多 hunk、多文件、新建文件和换行边界。
- 删除、重命名、二进制、重复路径、重叠 hunk、错误行号和上下文不匹配。

### 工具与文件安全

- `apply_patch` 在审批前完成全量解析、路径检查和预算检查。
- 审批期间文件或父目录变化时零写入。
- 多文件成功、提交中途失败后完整补偿、补偿失败后的实际状态报告。
- 新文件不覆盖、敏感路径拒绝、只读模式拒绝。
- Windows 与 POSIX 都继续走真实安全目录绑定和发布原语。

### Runtime、Shell 与 Session

- 一条任务内多个工具调用聚合为一条净 `TaskChangeSet`。
- Agent 最终未完成但已经落盘的变化仍可查看和撤销。
- `/diff`、`/undo` 解析为本地命令且绝不调用 Agent。
- 撤销修改文件、新建文件和混合多文件任务。
- 外部内容、mode、身份或删除变化导致整批冲突且零写入。
- 用户拒绝撤销、撤销中途补偿和补偿失败。
- 撤销成功恢复任务前的 `modified_files` 与 `verification`。
- Session 隔离、切换恢复、`/clear` 保留、模型切换保留、进程重启不恢复。
- SQLite 持久化失败时工作区状态和内存警告保持一致。

### 隐私与回归

- 审计和 SQLite 不出现补丁、源码、diff 或任务原文。
- `/diff` 动态内容按字面渲染，不能注入 Rich markup。
- 现有 Provider-native tool calling、工具定义、审批、Session 和完整测试套件继续通过。
- GitHub Actions 的 Windows/Linux × Python 3.11/3.12 矩阵继续全绿。

## 验收标准

1. Provider 能用一个 `apply_patch` 调用安全修改多个文本文件或创建新文件，不能删除文件。
2. 当前 Session 的 `/diff` 精确显示最近一条非空任务的净变化。
3. `/undo` 经冲突检测和人工审批后完整恢复任务前工作区状态，包括删除该任务新建的文件。
4. 外部修改存在时 `/undo` 零写入拒绝，不覆盖用户内容。
5. 各 Session 的账本隔离；退出进程后不持久化源码快照。
6. 只读、2,000,000 字符预算、路径策略和审计脱敏边界有自动化测试。
7. 本地完整测试、`compileall` 与四组合 GitHub Actions CI 通过。

## 暂不纳入范围

- 文件删除或重命名补丁。
- `/redo`、多级 undo、历史选择和跨重启恢复。
- Git index、commit、stash 或工作树恢复。
- 二进制补丁、Git binary patch 和非 UTF-8 文本。
- 三方合并或强制覆盖外部修改。
- 云端同步、加密源码快照和持久化备份清理。
