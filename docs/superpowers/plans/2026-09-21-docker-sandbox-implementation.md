# TriCoder Docker 沙箱：可行性检查与实施方案

日期：2026-09-21。状态：方案待实施。本文所有新接口、命令和模块名均为建议，尚未实现。

## 1. 结论与检查证据

架构可行，复杂度中高。无需重写 Provider、Agent 循环或会话记忆；需要增加执行后端、独立工作副本、容器生命周期和受控写回能力。不能只替换 run_command 的启动命令。

本次检查为只读代码检查和环境命令定位：
- tools/command.py：RunCommandTool 直接调用 run_bounded_process；GitDiffTool 同样运行宿主机进程；_git_toplevel 直接调用 subprocess.run。
- tools/__init__.py：ToolContext 集中注入工作区策略、命令策略、审批、变更账本和验证范围，适合作为后端接入点。
- policy.py：CommandPolicy 将程序解析成宿主机可信绝对路径，不能直接用于 Linux 容器。
- session_runtime.py：_build_active 创建工作区策略和 ToolContext，是交互会话的主要接入位置。
- cli.py、session_runtime.py、evals/service.py 均构建 ToolContext；evals/runner.py 另有验证进程入口，必须明确处理，不能遗漏。
- tools/undo.py、changes.py：已有修改记录、撤销冲突检查和失败补偿，可借用机制，但不能直接把副本文件身份当作原文件身份。
- verification.py：当前证据关联工作区快照，尚无容器镜像和副本版本绑定。
- evals/workspace.py：已有链接安全检查、隔离副本和指纹机制，可参考并按需提取小型公共函数，不直接复制评测专用逻辑。
- MCP/扩展有独立执行路径，run_command 容器化不会自动隔离它们。
- 当前 PATH 未找到 docker；不能据此断言系统完全未安装 Docker，但本次没有验证 daemon、WSL、镜像、挂载或真实容器。
- 工作区存在大量未提交改动，包括会话记忆修复；实施前重新核对，禁止覆盖或回退这些改动。

本轮未运行功能测试、未安装工具、未拉取镜像、未启动容器。项目文档中的历史测试通过记录不能作为本功能验证证据。

## 2. 首版范围与安全承诺

采用“宿主机控制 + 每会话独立工作副本 + 每次命令独立容器 + 确认后写回”。
- 支持 Linux 容器中的 Python 检查和测试。Windows 宿主机通过可用的 Linux Docker engine 运行。
- 不支持 Windows 容器、任意语言自动装环境、联网安装依赖、任意镜像、远程 Docker daemon。
- Provider、密钥、会话数据库、审计、审批、容器管理权留在可信宿主机进程。
- 容器只挂载工作副本，不挂载原项目、用户主目录、Docker socket、会话状态或凭据。
- 文件读写工具可以继续作为可信宿主机代码运行，但必须指向副本并维持严格路径绑定。这不是“全部工具都在容器内”的实现。
- 沙箱模式禁用未被纳入隔离的 MCP、外部扩展、外部 hooks；在注册或启动前拒绝，不仅隐藏工具描述。
- 原本 local 模式保持兼容；docker 模式必须显式选择，失败不能自动转为 local。任务进行中禁止切换执行模式。
- 默认断网、非 root、只读根目录、丢弃 capabilities、no-new-privileges；限制内存、CPU、PID、时间和输出。
- 不宣称容器绝对安全；宿主内核/daemon、镜像供应链仍是信任边界。工作副本的磁盘写入不能仅靠内存限制约束，见 P2/P3。
- “测试通过”仅表示特定镜像内、特定副本代码的测试通过，不等于 Windows 原生环境通过。

## 3. 数据流与核心状态

```text
用户选择 Docker 模式
  → 检查本地 Docker 与已存在的受信镜像
  → 从原项目生成筛选后的副本 + 原文件基线
  → Agent 使用副本进行读、改、搜索
  → 审批命令 → 容器执行 → 确认退出和清理 → 生成验证证据
  → 展示完整回写差异
  → 用户确认 → 再次校验原文件与副本 → 写回 + 单独记录原项目撤销账本
```

建议新增 sandbox/ 包，职责如下（允许按当前代码合理调整命名）：
- execution.py：ExecutionRequest、ExecutionResult、ExecutionBackend；LocalExecutor 和 DockerExecutor。
- workspace.py：SandboxWorkspace（原路径、副本路径、Session ID、generation、基线清单）。
- docker.py：镜像检查、固定参数启动、跟踪容器、停止、检查、清理。
- publish.py：发布预览、冲突检查、受控写回、失败补偿、原项目撤销记录。

ExecutionRequest 包含经过校验的逻辑 argv、相对 cwd、超时、输出预算和取消令牌。
ExecutionResult 至少包含退出码、输出、超时/输出超限、启动状态、清理证据；容器结果另含容器 ID 和真实镜像 ID。保持当前 ToolResult/ErrorCode 语义，必要新增错误码必须覆盖恢复分支。
不要将模型返回值或容器输出中的“通过”字段当作可信验证依据。

状态建议：PREPARING → READY → RUNNING → READY → PREVIEWED → PUBLISHING → PUBLISHED；
失败进入 FAILED 或 CLEANUP_UNCERTAIN。清理不能确认时禁止回写、并发新命令和销毁副本，保留人工排查信息。
Session 切换、取消和退出必须处理所属资源，不影响其他 Session。程序重启不恢复旧审批或旧验证能力。

## 4. 分阶段工程任务

### P0：固定行为与回归基线

阅读根/项目 AGENTS.md、README、project.md、pyproject.toml 和本文件；核对最新代码。
列出所有能创建进程、调用扩展、接触原工作区的入口。
先运行现有相关测试，记录环境与基线，不提交或清理已有用户修改。
新增配置设计保持 local 默认；Docker 环境缺失时返回清晰错误。
产物：入口清单、基线结果、最终模块划分。无需等待逐阶段批准。

### P1：抽出执行后端，保持 local 行为

改造 ToolContext、RunCommandTool、GitDiffTool 及 Git 根目录探测。
把命令解析/参数策略与可执行文件定位拆开：
- local 使用原有宿主机可信程序定位。
- docker 使用受信镜像内固定程序映射，不能在副本中通过 PATH 查找同名程序。
- 模型不能传 Docker 参数、镜像名、挂载源、容器 ID 或任意环境变量。
- 不通过 shell 拼接参数，不因为用了容器而删除现有审批和命令策略。

统一 CLI、SessionRuntime、Eval 的构造入口，避免只有交互模式生效。
对 evals/runner.py 明确区分可信评测控制逻辑与运行项目代码的验证命令；后者在 Docker 模式必须走沙箱。隐藏评测材料不得因此暴露给 Agent。
测试：local 原行为；backend 请求和返回映射；各入口选择一致；Docker 不可用时无本机回退。

### P2：独立副本与完整文件视图

副本放本项目 runtime/docker-sandbox/<session>/<generation>/workspace；控制元数据放 workspace 的同级，不挂载到容器。
原项目标识保持不变，另存 execution_workspace，不能把临时路径作为用户会话的项目身份。
按可信清单筛选，复制前检查普通文件、链接和边界；拒绝符号链接、junction、reparse、特殊文件与可识别外部硬链接，不允许复制时跟随链接。
排除 .env*、凭据目录、.git、.venv、runtime、会话/审计文件等；保留必要源码与测试。隐藏文件不等于一律排除。
路径规则无法发现源码中硬编码的所有秘密，文档必须说明此限制；不要读取真实密钥以“验证过滤”。
设置文件数、单文件和总复制字节预算，防止递归复制自身。复制前后核对身份/版本，源文件变化时拒绝混合基线。
同一会话内文件工具串行操作；容器运行期间不并发扫描、编辑、预览或回写副本。

首版不复制真实 .git：git_diff 由基线与副本比较实现并保持其只读统计语义；run_command 中 git show/log 等需要历史的命令明确不支持，不回到原仓库运行。必要的 status/diff 能力使用本地可信差异实现，不执行副本中可控 Git 配置。
测试：两个 Session 隔离；未提交源码被纳入；原项目保持不变；链接/特殊文件/大小预算/敏感路径被拒绝；取消复制不留下可激活的半成品。

磁盘边界：可写 bind mount 可能填满其所在磁盘。首版必须限制执行时间、监测副本大小并在超预算时终止，同时明确监测是软限制、有竞态。若部署要求硬磁盘配额，需使用平台支持的独立限额存储并完成真实验证，未实现前不能声称具备硬磁盘隔离。

### P3：Docker 生命周期与执行约束

优先使用受控 Docker CLI 适配器，不新增 Python SDK 依赖。只有可信宿主进程可调用 Docker。
要求本地可信 engine，拒绝任意 DOCKER_HOST/远程 context；Docker CLI 与配置由用户控制，不读取或打印认证内容。
使用已存在并经授权选定的镜像，固定 digest/实际 image ID；不自动拉取、构建或安装依赖。
镜像必须预装 Python 与本项目测试所需依赖。不可直接复制 Windows .venv；首版使用 unittest 合成 fixture 验收，额外工具需对应镜像支持。
覆盖镜像默认 entrypoint，固定用户、工作目录、PATH；校验镜像声明的 volumes 等不会引入意外可写挂载。

每次命令新建容器，只共享该 Session 的副本。默认 network=none、read-only root、cap-drop=ALL、no-new-privileges、有限 tmpfs、CPU/内存/PID 限额，无特权、设备、端口或主机命名空间。
使用固定 argv，镜像检查/创建/启动/等待/inspect/停止/删除每步均有期限。容器启动前可追踪其唯一 ID、所有权标签和本地记录，避免取消发生后留下未知容器。
Docker 客户端退出不等于容器退出。超时/取消/输出超限都必须停止实际容器，检查停止结果后再清理；只有完全确认才能继续使用副本。
限制日志存储，不能只截断客户端显示却让 daemon 无限写日志。停止后再做稳定快照。
daemon 失联时标记结果和清理不确定，不声称撤销或终止成功。恢复仅操作本任务确认拥有的资源，禁止全局 prune 或按不唯一名字批量删除。
测试：构造参数；创建/启动边界取消；超时；后台子进程；输出洪泛；OOM/PID 上限；daemon 中断；容器残留和跨 Session 清理。

### P4：验证、预览回写和撤销

验证证据至少绑定 Session/generation、副本快照、实际镜像 ID、命令和成功退出/清理结果。
副本修改、镜像变化或清理不确定会使旧证据失效。已有 unknown_effects 不因“进入 Docker”自动清零。

拟新增本地命令 /sandbox status、/sandbox diff、/sandbox apply（命名可按现有命令体系调整）：
- status 显示执行模式、原工作区、副本、镜像、清理状态和“原项目尚未写回”。
- diff 显示拟写回的全部变更及不支持的变更。
- apply 先精确预览，再人工确认，提交时重验会话、generation、基线、副本版本与原文件身份/内容。任何变化使旧预览失效。
- 回写目标只允许原项目边界内的普通文件；首版仅支持有界 UTF-8 文本新建/修改。删除、重命名、二进制、权限变化、链接或特殊文件必须明确拒绝整次回写，不能静默忽略。
- 可明确排除固定的测试缓存等运行产物，但必须展示排除清单；不得在声称完整通过的情况下任意筛掉业务修改。
- 针对每个受影响原文件保存初始内容/身份。确认到提交之间以及逐文件写入前重新校验，避免覆盖用户或其他会话改动。
- 多文件写回不是天然原子事务：先全量检查，再受控逐项提交；部分失败须补偿，补偿失败记录不确定状态、停止自动操作，提供明确的受影响路径。
- 原项目写回使用独立 ChangeJournal；不能直接复用副本 inode/文件身份。新增文本发布变更可供原项目撤销，继续要求冲突检查与确认。
- 区分“撤销副本内工具修改”和“撤销已写回原项目”。不得让 /undo 静默切换目标。单独提供明确的发布撤销入口或目标选择，并测试。
- 发布成功后更新副本基线；再次 apply 无重复变更。拒绝/取消不会修改原项目。发布过程禁止运行任务/切换会话。
- 发布后的验证只标注该内容版本在容器环境测试通过；不自动声称原工作区环境测试通过。

测试：正常多文件回写与撤销、原文件外部修改、创建目标抢占、会话切换、过期预览、部分写入失败/补偿失败、重复 apply、不可支持变更、只读模式拒绝写回。
重启后的待发布副本只作为未验证草稿，重新核验；不恢复审批和验证能力。不自动删除用户尚未发布的工作成果。

### P5：入口集成、真实隔离验证和交付

CLI/Shell/TUI 展示模式、镜像、副本状态和发布结果；等待容器期间 UI 可取消。Agent 的 finish 成功不等于已发布到原项目，界面必须分开显示。
沙箱模式在 MCP/扩展启动之前实施禁用策略，覆盖单次 CLI 和交互会话。可信 Provider 网络请求不受容器断网影响，密钥不进入容器环境。
会话切换、模型切换、清空记忆、恢复会话均不得错绑副本或清理另一会话资源；清空记忆不自动丢弃未发布代码。

测试分两层：
1. 无 Docker：假执行后端/假 Docker 控制器 + 合成临时文件，覆盖状态机、策略、失败注入、三个入口与 local 回归。
2. 真实 Docker：用户已提供环境和批准测试后，使用无秘密 fixture；验证容器看不到宿主测试哨兵、容器网络被关闭、环境中无合成密钥、原项目不被误删、多会话隔离、资源限制、取消无存活容器、差异确认写回与撤销。

不得用真实用户文件、真实凭据或真实 Provider 验证隔离；不要以恶意测试破坏宿主。合成测试仅在专用临时目录和受限容器执行。
真实 Docker 不可用时仍完成可独立实施的代码、模拟测试和文档；记录 Docker 集成未验证，不能把跳过当通过或宣称生产可用。

最终运行相关专项、全量 unittest、语法检查、git diff --check；运行命令以项目当时测试入口为准。
证据放 runtime/docker-sandbox-implementation/，包含测试数量、失败/跳过原因、平台、Python/Docker/镜像版本、未验证项；不要保存秘密或原始敏感输出。
更新 README、project.md 和配置示例，说明默认 local、镜像准备、首版限制、恢复方式与审批边界。

## 5. 阶段验收与回退

| 阶段 | 完成标准 | 不可接受的替代 |
| --- | --- | --- |
| P0/P1 | 原行为回归通过；所有入口可选择同一后端 | 只改 Shell 或只给命令加 docker 前缀 |
| P2 | 文件工具与命令看同一副本，原项目无变化 | 直接可写挂载原项目 |
| P3 | 确认实际容器退出；缺 Docker 拒绝执行 | 杀 Docker CLI 后报告清理成功 |
| P4 | 精确预览、冲突检查、失败补偿、发布撤销闭环 | 整目录覆盖或假称全量原子回写 |
| P5 | 模拟测试和真实容器结果分别报告 | 把跳过集成测试算成沙箱已验证 |

回退是显式使用 local 配置并新开会话，不做代码 reset 或删除数据库；必须告知用户 local 不具备容器隔离。清理未完成前禁止把同一工作副本交给 local 继续运行。
变更按阶段保持最小可审查差异；未经授权不提交、推送、重建仓库或安装依赖。

## 6. Docker 环境前置条件与参考

当前 docker 不在 PATH：coding 会话先复查，不擅自安装。环境补齐、镜像下载/构建、运行真实容器需按工作区规则获得相应授权；与用户沟通时写明具体操作和原因。此限制不阻止接口实现和模拟测试。
Windows Docker Desktop 的系统/WSL 前置条件和授权条件按官方当前说明核对，不假设已经满足。

官方依据（2026-09-21 查阅）：
- 运行参数、退出状态、资源限制：https://docs.docker.com/engine/containers/run/
- bind mount 会改变宿主机对应目录：https://docs.docker.com/engine/storage/bind-mounts/
- Windows Docker Desktop 前置条件：https://docs.docker.com/desktop/setup/install/windows-install/
- 容器安全边界：https://docs.docker.com/engine/security/

采用 Docker 作为外部执行引擎，不复制外部仓库源码。若后续决定新增 SDK、复用外部代码或镜像依赖，应另行核对来源、许可、版本、维护及供应链风险。
