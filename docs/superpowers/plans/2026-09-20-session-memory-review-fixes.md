## 3. R1：预览绑定会话与原始状态

### 问题位置和触发方式

- `src/tricoder/session_runtime.py`：MemoryEditPreview、MemorySavePreview、preview_memory_edit、apply_memory_edit、preview_memory_save、save_memory_preview。
- 当前 apply_memory_edit 核对 revision、next_message_seq 和 pending-clear，但未核对 session_id、generation 或完整的预览前记忆。
- 复现条件：A/B 的 revision=1、next_message_seq=2；两者约束不同。A 生成编辑预览后将 current 切换为 B，提交 A 预览，B 被替换成 A 的候选。
- 保存路径目前比较完整候选，条件更严格；不能据此声称它已有相同的内容覆盖漏洞，但仍应补齐会话身份绑定。

### 修改方案

- [x] 给两种预览增加 session_id、generation、预览前的完整 ConversationMemory 快照和 next_message_seq；保存预览继续保留数据库 expected_revision。
- [x] 在任务锁内检查：当前会话、generation、原始记忆快照、消息序号均与预览一致；保存额外核对数据库版本和持久化模式。
- [x] 检查通过后再应用 candidate。任意不匹配均要求重新预览，不能自动把旧预览重定位到当前会话。
- [x] 提交入口再次校验候选结构；敏感内容检查不能仅依赖曾经打开过预览。检查不通过用固定错误，不输出原文。
- [x] 编辑确认后增加 revision，使重复提交同一编辑失败。保存不得在冲突时覆盖写入；相同版本重复保存的幂等行为明确写测试。
- [x] 本地来源编号继续绑定正确会话；预览内存对象不能放进审计正文。

### 测试

建议新增 `tests/test_memory_preview_binding.py`，并扩展现有 memory lifecycle/persistence 测试：

| 用例 | 预期 |
| --- | --- |
| A 预览后切到同 revision、同序号的 B | 拒绝；A/B 内容均不变 |
| A/B 候选内容也相同，但 Session 不同 | 保存仍拒绝；不得在 B 意外新增记录 |
| 相同计数但原记忆内容变化 | 拒绝编辑 |
| /clear 后提交旧预览 | 拒绝，即使人为构造相同其他计数 |
| 同会话、状态未变、有效确认 | 正常应用/保存 |
| 同一编辑重复提交 | 第二次拒绝，不新增来源或重复修改 |
| CLI/TUI 在预览等待期间尝试切换 | 明确记录是否可达；无论 UI 如何，runtime 都应拒绝陈旧预览 |

完成标准：真实方法的跨会话复现由接受变为拒绝，并检查数据库和内存没有部分写入。

## 4. R2：保存前覆盖最新已完成历史

### 问题位置和表现

- `src/tricoder/context/manager.py`：plan_review_compaction 默认保留最近两个任务。
- `src/tricoder/agent.py`：prepare_review_memory 复用该计划。
- `src/tricoder/session_runtime.py`：preview_memory_save 直接预览已有 conversation_memory。
- 这适合作为压缩策略，但不能保证“保存当前会话”的内容完整。低于压缩阈值的一两轮会话可能只有空摘要；长会话也遗漏最近两项任务。

### 修改方案：将压缩和保存候选生成分开

- [x] 保留运行中上下文压缩策略，不通过简单修改 keep_recent_tasks 来解决保存问题。
- [x] 新增独立的保存候选准备流程：读取旧记忆和覆盖位置之后所有已结束任务，包括最后一个已完成任务。
- [x] 只有执行层明确结束、且工具调用/结果配对完整的任务才进入候选。取消、未闭合调用和未确认状态不伪造成完成事实；不能因“没有下一个 task 标记”就忽略最后任务。
- [x] 保存候选准备调用无工具 summarizer，复用现有超时、取消、失败分类与预算；本地 `/memory save` 命令本身不进入业务对话。
- [x] 在候选准备开始时捕获 generation、revision、历史快照和结束位置；运行时提交和保存预览分别再次核验，发现变化则丢弃候选。
- [x] 候选生成可以增加模型请求，但不会在 SQLite 事务中等待模型。
- [x] 生成保存候选时不删除近期原始消息，也不提前修改当前正式记忆；预览展示确切 JSON、保存位置和覆盖位置。
- [x] 用户确认后再次核验 R1 的绑定并事务保存；拒绝或取消不保存，成功后才更新已保存版本标记。
- [x] 保存候选与运行时摘要使用独立字段，直到重启加载，不靠 covered_through 隐式删除近期历史。
- [x] 没有新内容时复用已有候选，不新增总结请求；无法完整覆盖时明确拒绝。

超长保存输入按完整任务块有界处理，每次保存最多两批模型总结；仍不能覆盖时明确拒绝完整保存，保留状态并提示先整理，不保存一份标称完整但实际缺尾部的记忆。敏感内容检查与人工确认继续生效。

### 测试

建议新增 `tests/test_memory_save_coverage.py`：

1. 一个完整任务且从未触发压缩：save 候选包含该任务目标/约束，确认后重启可恢复。
2. 两个完整任务：第二个任务的新增约束被覆盖。
3. 多任务：保存覆盖最新已完成任务，近期内存消息不被提前删除。
4. 保存后继续聊天：没有重复摘要注入、编号回退或覆盖边界错乱。
5. 拒绝确认、总结失败、切 Session、clear、数据库失败：不保存陈旧/不完整结果。
6. 未闭合工具组、超预算输入：明确失败，调用次数有界。
7. persistence=off：不允许语义保存、不增加总结请求。

完成标准：先前一两轮无法保存任务语义的场景通过，并且运行中记忆与保存候选不会相互污染。

## 5. R3：为记忆增加更新和容量处理

### 问题位置和表现

- `src/tricoder/context/memory.py`：merge_candidate 对已有 ID 跳过、对新 ID 追加；已有 goal 保持不变。
- 每类 MAX_ITEMS_PER_SECTION=20，另有总长度上限。第 21 个新增待办导致合并失败；不同 ID 表达同一内容也会占用更多条目。
- 旧约束被保护是有意设计，不能简单允许模型任意改写。需要按信息类型区分维护方式。

### 推荐首版设计

| 类别 | 维护方式 |
| --- | --- |
| 用户约束 | 不自动删除或改写；明确用户确认才替换，保留 scope/task_id |
| 待办 | pending/done/cancelled；模型提出状态变化候选，用户确认后变更，不因模型声称完成就认定执行成功 |
| 决策 | active/superseded；替代要引用旧条目 ID，明确显示差异并确认 |
| 目标 | 按 task_id 标识所属任务；新目标不能静默覆盖旧任务目标，也不能永远固定第一个目标 |

### 2026-09-20 实施决议

- schema 升级为 v2：`MemoryItem` 增加固定枚举 `state` 和可选 `replaces_id`；旧 v1 正常加载时，待办映射为 `pending`、决策和目标映射为 `active`，约束固定为 `active`。未知版本继续拒绝。
- `ConversationMemory` 增加带原类别的有界归档。`done/cancelled` 待办、被替代决策和旧目标在待保存候选中移入归档；归档会进入精确保存预览和 v2 持久化，但不会默认注入模型请求。
- 运行时压缩继续使用保守合并，同 ID 改写不会立即影响模型上下文。独立 `review_memory_candidate` 可以携带模型提出的状态/替代变化，但只有 `/memory save` 的精确预览确认后才持久化；本地 `/memory edit` 仍有独立预览确认。
- 决策替代必须由新条目的 `replaces_id` 引用现有 active 决策；新任务目标在待保存候选中替代旧目标并归档旧目标，预览会展示两者。约束不会被模型自动归档或删除。
- 每类最多 20 个活跃项，归档总数最多 40。接近上限时只自动整理已终结/被替代项到待确认候选；若活跃内容仍超限，抛出可操作的容量错误并保留旧记忆和原始历史。该行为不靠提高原活跃上限解决。

这些状态只描述语义记忆，不是工具执行/测试成功的证据。初版采用可见的候选更新＋本地确认，不引入模型自主清理关键约束。

- [x] 在 memory.py 设计兼容版本的新字段和状态校验；修改 summarizer 提示、解析器及序列化，不只改 dataclass。
- [x] 新旧 schema 明确转换：旧待办映射 pending，旧决策映射 active；转换只作用合成测试库和正常加载路径，不直接操作真实数据库做试验。
- [x] 新目标或状态冲突形成待确认变更；预览绑定 R1 的身份和版本，并明确展示被替代条目。
- [x] 对相同 ID 的新增、更新、完成进行区分；重复文本只做严格标准化去重，不合并语义相近的约束。
- [x] 条目/字符上限给出可操作容量错误；已完成/被替代条目经候选预览确认后进入归档，而非提高活跃上限。
- [x] 活跃内容仍超过上限时要求用户选择，保持旧记忆和原历史，不自动丢弃约束。
- [x] 归档不默认发送给模型；归档有界并纳入 v2 精确保存预览和重启恢复。
- [x] 本地记忆编辑、保存和恢复支持固定枚举状态；CLI/TUI 均提供状态选择。

在实施本项前，将实际选择的新 schema、转换和确认方式补充到本文件或项目设计记录，随后实施。日常实现细节无需反复询问；若决定取消人工确认、自动遗忘约束或保存额外私有内容，则超出此方案。

### 测试
